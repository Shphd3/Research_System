# Group Meeting Script: Real-Text Common-Logit Audit

## **Opening**

我这轮想回答一个真实文本问题：前面 toy 任务里，我们看到共同分量可能让路由器偏向少数专家；那么在 DCLM 真实文本里，随机初始化的线性稀疏混合专家路由器是不是也有这种专家选择偏置？

这里我主要区分三种解释。

第一，是不是共同分量在第 0 步就已经主导路由。第二，是不是只是高频词元太多导致少数专家被频繁选中。第三，是不是初始化只有偏置，但训练早期把这个偏置快速放大。

## **Conclusion**

结论是：真实文本没有支持“第 0 步共同分量已经主导路由”的强版本。第 0 步主要专家分数间隔来自词元自身差异，而不是共同分量。

但是，初始化路由器确实存在专家选择偏置。共同分量会增加负载集中；单专家硬选择最明显；高频词元不是主因；训练前 10 步会把这个偏置快速放大。

所以我现在不把这个现象称为硬坍塌，而称为负载集中。硬坍塌意味着专家基本死亡；负载集中意味着专家可能都被用到，但大部分词元被少数专家吸收。

## **Evidence 1: Step-0 Common Component**

第一个关键数字是共同分量占优比，也就是共同分量造成的专家分数间隔除以词元自身差异造成的专家分数间隔。

结果是：

```text
common_margin = 0.1237
residual_margin = 0.2364
dominance_ratio = 0.5251
```

18 个层和种子的组合里，只有 1 个组合的占优比大于 1。

这说明第 0 步共同分量主导路由这个强结论不成立。真实文本里，第 0 步单个词元的路由分数主要还是由词元自身差异决定。

## **Evidence 2: Common Component Still Biases Load**

第二个关键数字是最大专家负载。

原始路由中，最大专家接收 27.81% 词元；去掉共同分量以后，最大专家负载降到 15.61%。

```text
raw_max_load = 0.2781
centered_max_load = 0.1561
delta_max_load = 0.1220
```

这说明共同分量不是无关噪声。它虽然不是第 0 步最大的分数间隔来源，但作为所有词元共享的偏置，会把更多词元推向少数专家。

## **Evidence 3: Top-1 Exposes the Bias Most Clearly**

第三个审计是看初始化下 `top-k` 专家选择是否集中。这里的 `top-k` 只是读取同一个初始化路由器分数最高的 k 个专家，不是重新训练 `top_k=2/4` 模型。

如果 8 个专家完全均匀，每个专家选择占比应该接近 0.125。

结果是：

```text
top-1 max selection share = 0.2781
top-2 max selection share = 0.2303
top-4 max selection share = 0.1794
```

所以初始化确实有专家选择倾向，并且单专家硬选择最明显。读取更多专家会缓解这个初始选择偏置，但现在还不能说 `top-k` 训练能解决问题，因为这一步没有重新训练模型。

## **Evidence 4: Frequent Tokens Are Not the Main Cause**

第四个审计是排查高频词元。

DCLM 打包文本里，高频词元确实很多：

```text
top10 token ids = 19.58% tokens
top50 token ids = 37.48% tokens
top200 token ids = 52.72% tokens
```

但去掉这些高频词元以后，最大专家选择占比基本不变：

```text
all tokens top-1 max share = 0.2781
not top200 top-1 max share = 0.2739
```

如果集中主要由高频词元造成，去掉 top200 后应该明显下降；实际几乎没有下降。因此高频词元会轻微加重集中，但不是主因。

这里需要区分两个概念：common tokens 是数据里频繁出现的词元编号；common component 是隐藏状态向量中共享的方向 $c$。这轮结果说明，不能把路由集中简单归因于 common tokens。

## **Evidence 5: Early Training Amplifies the Bias**

第五个证据是训练前 10 步。

实际专家数为 8 时，第 10 步结果是：

```text
dominance_ratio = 21.7874
raw_max_load = 0.8507
effective_experts ~= 1.96
raw_active_experts_ratio = 1.0000
```

这几个数字要一起看。8 个专家都至少被激活，所以不是专家全部死亡。但是最大专家吃掉 85.07% 词元，有效专家数只有约 2 个，所以负载已经高度集中。

因此，判断路由是否健康不能只看专家是否被激活，还要看最大专家负载、有效专家数、路由分布熵和负载不均匀系数。

## **Setup**

实验设置是一个随机初始化的小型 Qwen 风格因果语言模型：

```text
num_layers = 6
hidden_size = 512
attention_heads = 8
kv_heads = 4
expert_hidden_dim = 2048
num_experts = 8 for main training trajectory
```

数据是 DCLM 打包文本：

```text
sample_span = 257 tokens
input_tokens = 256
target_tokens = shifted next 256 tokens
padding = none
audit_sequences = 8192
train_sequences = 32768
```

路由器是标准稀疏混合专家路由：

```text
router_type = linear
router_input = actual hidden state entering the gate
top_k = 1
shared_expert = false
load_balance_loss = 0.0
oracle_gating = false
multihead_routing = false
```

这里没有共享专家，也没有负载均衡损失。任务损失会通过概率函数更新所有路由向量，但每个词元只有被选中的专家前馈网络参与计算。

## **Interpretation**

现在我对机制的理解是：真实文本隐藏状态有整体几何偏置；随机线性路由器会把这种偏置转成专家选择倾向；单专家硬选择让这种倾向更明显；训练早期进一步放大这个偏置，形成严重负载集中。

这和 toy 结果不是完全矛盾，而是时间点需要修正。toy 里共同分量在第 0 步就很强；真实文本里共同分量在第 0 步只是偏置源，不是主导源，但它会被训练早期快速放大。

## **Boundary**

这轮结果能说明：在这个小型随机初始化模型和 DCLM 文本设置下，共同分量是负载偏置源，单专家硬选择会暴露偏置，早期训练会放大偏置。

这轮结果还不能说明：预训练大模型一定存在同样现象，也不能说明专家已经学到了或没有学到可解释功能，更不能说明 `top-k` 训练或某个去共同分量方法已经能解决问题。

## **Next Step**

下一步我不先做复杂新方法，而是先定位第 10 步放大来自哪一路。

我会做三个最小因果拆分。

第一，冻结路由器权重，看没有路由器更新时，第 10 步负载集中是否还在。

第二，冻结隐藏状态生成层，看隐藏状态变化是不是放大的主要来源。

第三，冻结专家输出反馈，或者切断专家反馈，看早期被选中的专家是否继续强化已有路由。

如果某个冻结条件显著压低第 10 步共同分量占优比和最大专家负载，就能决定下一步方法方向：是共同分量约束初始化、路由输入控制，还是早期防锁死训练。

## **Closing**

所以本轮最稳妥的结论不是“真实文本已经证明共同分量导致硬坍塌”。

更准确的说法是：真实文本中存在初始化专家选择偏置；共同分量和单专家硬选择会暴露这个偏置；高频词元不是主因；训练早期会把它放大成严重负载集中。

下一步是做因果拆分，找到放大路径，然后再决定方法方向。

## **Likely Questions**

**Q1: 这是不是 collapse？**

不是硬坍塌。更准确是负载集中。第 10 步所有 8 个专家都至少被激活，但最大专家吃掉 85.07% 词元，有效专家数只有约 1.96。

**Q2: 共同分量机制是不是失败了？**

强版本被削弱：第 0 步共同分量不主导分数间隔。弱版本成立：共同分量会造成负载偏置，去掉它后最大负载明显下降。训练早期还会把这个偏置快速放大。

**Q3: 是不是高频 token 太多导致的？**

不是主因。top200 高频词元占全部词元 52.72%，但去掉后最大专家占比仍是 0.2739，和全量 0.2781 很接近。

**Q4: top-k 能不能解决？**

现在只能说读取 `top-k` 会缓解初始化选择偏置。这里没有重新训练 `top-k` 模型，所以不能声称 `top-k` 训练可以解决问题。它可以作为后续方法对照。

**Q5: 为什么下一步不直接做方法？**

因为现在已经知道第 10 步发生快速放大，但还不知道放大来自路由器权重、隐藏状态变化，还是专家反馈。先定位放大源，才能决定方法是初始化、路由输入控制，还是早期防锁死训练。
