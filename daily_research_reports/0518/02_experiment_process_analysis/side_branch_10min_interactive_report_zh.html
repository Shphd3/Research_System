概念澄清

Expertise 不是“被选中”

一个 expert 只是被 router 选中，不代表它有专业化。我们要求它稳定负责某类 rule，并且禁用它会选择性伤害对应 rule。

Load balance 不是 expertise

负载均匀只能说明 token 没全挤到一个 expert。它可能按位置、噪声或 common pattern 切分，不一定按 rule 切分。

Oracle-space 是语义地盘

这里用 warmup 模型的 rule-context `ffn_input` 表示做 KMeans，得到 cluster centers，再把它们作为 prototype router 的初始地盘。

Inhibition 要守地盘

winner attraction、loser repulsion、homeostasis 的目标不是让 load 好看，而是防止 expert basin 互相吞并。

Performance feedback 是功能约束

它问哪个 expert 对当前 token loss 更低。但如果不保护 Oracle clusters，它可能把多个 rule 合并给当前最强 expert。

实验详情

Oracle-initialized router 到底验证了什么？

方法
warmup MoE -> 抽 rule-context `ffn_input` -> KMeans -> centers 初始化 prototype router -> 从同一 warmup checkpoint 继续训练。
为什么要 warm-start
centers 必须和 router 输入在同一表示空间；否则坐标系不一致，实验无效。
结论
`oracle_init` NMI 0.964，3/4 seeds 四分。Oracle-space signal 不只是 probe 指标，而能转成 routing。
边界
seed 2 warmup KMeans NMI 0.800、purity 0.750，下游也只到 3 experts。

Inhibition 为什么不是直接答案？

它做什么
winner attraction、loser margin、homeostasis，目标是让 expert basin 更稳定。
正面结果
`oracle_init_inhibition` 把 ablation drop 提到 0.687，是这一组最高。
问题
4-expert runs 从 oracle_init 的 3/4 降到 2/4，说明它可能增强因果瓶颈，但扰动 rule purity。
下一步
做系数 sweep，目标是在不牺牲 NMI 的情况下提高 ablation drop。

Performance feedback 为什么有用但危险？

它做什么
让多个 expert 都试算，哪个 expert 对 token loss 更低，就把 router 推向谁。
正面结果
`oracle_init_performance` 把 max all-token load 降到 0.458，明显缓解一般 token collapse。
问题
4-expert runs 只有 1/4。它可能奖励当前最强 expert 接手多个 rule，从而合并 clusters。
下一步
做 cluster-preserving performance feedback，让功能反馈服务于 Oracle cluster assignment。

Residual removal 到底说明了什么？

论文是否提到
Oracle-MoE 论文没有提出 residual removal；图注只是说图里省略 residual。
实验发现
no-FFN-residual 降低 load collapse、增强 ablation，但仍没有稳定四分。
解释
它解决 expert 是否必要，不解决 expert 应该负责哪个 rule。

支线总报告：这条支线到底回答什么

总览

核心问题

主线已经发现：默认 top-1 MoE 能学会 synthetic rules，也会产生 causally meaningful expert use，但不会稳定形成 `4 rules -> 4 experts`。支线要解释这个负结果，并寻找能让 expertise 出现的额外机制。

支线分解

层次问题当前判断
Residual是否 shared bypass 让 expert 不必要？部分是；去 residual 增强 bottleneck，但不四分。
Capacity架构能不能表达四分？能；supervised router 8/8 seeds 四分。
Oracle-space表示空间有没有 rule geometry？有；probe 与 Oracle-init 都支持。
Inhibition竞争机制能不能自己发现 experts？随机版本不够；必须守住 Oracle clusters。
Performance功能反馈能否补上约束？能打开 load，但可能合并 rule。

总判断

默认 objective 缺少 route-level specialization pressure。Oracle-space initialization 是目前最强正结果；inhibition 和 performance feedback 不是错，但要设计成 cluster-preserving，否则会牺牲 rule purity。

为什么这些方法有的 work、有的不 work

  • 能 work 的方法，通常补上了“router 应该按什么语义结构分”的约束。
  • 不 work 的方法，通常只改变了瓶颈强度、负载分散或随机竞争，却没有告诉 expert 地盘在哪里。
  • 部分 work 的方法，说明它补了一层约束，但会破坏另一层约束，比如 performance feedback 打开 load，却可能合并 rule clusters。

Inhibitory Competition 理论报告

机制假说

它想解释什么

普通 MoE 的 expert 只是一个被 router 选中的 FFN。理论报告提出更强定义：expert 应该是语义空间中的 attraction basin，也就是某类 feature 会稳定流向它，它也逐渐变成处理这类 feature 的功能单元。

核心机制

Winner attraction
靠近

赢的 expert prototype 向当前 feature 靠近。

Loser repulsion
推开

相近但没赢的 expert 被推离，减少地盘重叠。

Homeostasis
防垄断

避免单 expert 吞掉所有 token，但不把均匀 load 当作目标。

实验后的修正

随机 prototype + inhibition 不够，说明“竞争”不能从随机地盘开始。Oracle-initialized router 的正结果说明，inhibition 更合理的位置是：先有 Oracle-space 地盘，再用 inhibition 守住并增强因果性。

为什么这个理论可能 work

  • 默认 top-1 MoE 有正反馈：早期 winner 获得更多 route 和梯度，会继续变强。
  • 如果没有 loser repulsion 和 homeostasis，expert 地盘容易被早期偶然优势吞掉。
  • 如果先有 Oracle-space 地盘，inhibition 可以从“随机竞争”变成“守住已有语义边界”。

为什么最小版本没 work

  • 随机 prototype 没有站在 rule clusters 上，竞争会硬化随机 basin。
  • margin inhibition 只知道 winner 分数要高，不知道 winner 是否真的对应正确 rule。
  • homeostasis 防垄断，但它本身不知道什么是语义专业化。
源文件：semantic_moe_inhibitory_competition_theory_zh.md

FFN Residual Ablation 报告

有用但不充分

问题

论文里是否说去掉 residual 会更好？答案是否定的。PDF 中 residual 只出现在图注 “Residual connections are omitted.”，意思是图中省略，没有把 residual removal 作为方法主张。

实验设置

扫 `ffn_residual_scale in {1.0, 0.5, 0.25, 0.0}`，看去掉 FFN residual 是否让 expert 更必要，并是否诱导更清楚 rule experts。

ScaleMin target probRouting NMIRule expertsMax all loadAblation drop
1.00.93960.5012.000.9570.760
0.50.94910.4191.750.9590.855
0.250.96460.4191.750.9660.916
0.00.96240.6472.250.5660.966

结论

去掉 FFN residual 后，一般 token 的 load collapse 明显下降，expert ablation 更强；但仍没有稳定四分。所以 residual bypass 是问题的一部分，不是 semantic expertise 的充分解释。

为什么它会 work 一部分

  • FFN residual 是共享旁路，模型可以不用认真依赖 expert 也完成预测。
  • 降低 residual 后，expert 输出更接近必经路径，所以 ablation drop 变大。
  • all-token load 从约 0.96 降到约 0.57，说明训练动力学确实被改变。

为什么它不够

  • 它只回答“expert 是否必要”，不回答“哪个 rule 应该给哪个 expert”。
  • 没有 route-level semantic target，多个 rule 仍可合并到同一个 expert。
  • 所以 bottleneck pressure 不是 expertise pressure。

Supervised Router Positive Control 报告

容量正控

问题

默认 MoE 不四分，到底是架构做不到，还是训练目标不提供分工压力？这个实验只在 planted rule context 上给 router 正确 expert target，测试容量上限。

结果

ConditionRuns4-expert runsMin target probRouting NMIRule expertsExpected acc
baseline800.93900.5732.120.344
supervised880.87591.0004.001.000
supervised_no_ffn_residual880.88351.0004.001.000

结论

当前架构完全能表达 `4-rule/4-expert`。默认 MoE 的失败不是 capacity 问题，而是 ordinary next-token loss 没有提供 route-level 分工压力。

为什么它 work

  • 它直接给 router 一个 rule-to-expert 信号，消除了 routing 对称性。
  • 每条 rule 在 planted context 上被推向固定 expert，expert 因此获得稳定、专门的梯度来源。
  • 这说明模型容量、expert 数量和优化基本都足够。

为什么它不是最终方法

  • 它用了显式 rule label，是 positive control，不是无监督机制。
  • 它证明“能做到”，不证明默认 objective 会自己做到。
  • 它给 Oracle/inhibition 方法提供上界：无标签方法应该朝这个结构靠近。

Oracle-space Probe 报告

信号验证

问题

不看 learned router，只看模型内部 rule-context 表示，这些表示能不能被 KMeans 聚成 rule clusters？如果能，说明 Oracle-MoE 的语义空间思路在 synthetic D3 上有可用信号。

结果

ConditionRunsKMeans NMIPuritySame-minus-diff cosinePrev-context attention
baseline80.8640.8440.58050.2869

结论

baseline learned router NMI 约 0.573，但表示空间 KMeans NMI 已经有 0.864。模型内部已经有 rule geometry，只是默认 router 没有把它转成 expert 分工。

这只是 probe，不等于完整 Oracle-MoE 验证。后续 Oracle-initialized router 实验才把 cluster centers 接进 routing。

为什么它提示 Oracle-MoE 可能 work

  • 如果 rule-context representations 已经聚成簇，router 就不需要从零发现所有结构。
  • KMeans NMI 高于 learned router NMI，说明“表示空间知道，但 router 没用好”。
  • 这正好对应 Oracle-MoE 的思路：先找 semantic group / oracle space，再用它指导 routing。

为什么 probe 本身还不够

  • KMeans 是离线诊断，不能证明训练中的 router 会保持这些 clusters。
  • 它不测 expert ablation，不知道 cluster routing 是否有因果作用。
  • 它也没有验证论文里的 attention semantic group、SVD projection 和 locality/CSD 指标。

Prototype / Inhibition 报告

随机地盘失败

问题

不用 rule label，只给每个 expert 一个随机 learnable prototype，再加 winner attraction、margin inhibition 和 homeostasis，能不能自己形成 rule expertise？

结果

Condition4-expert runsMin target probRouting NMIRule expertsMax all loadAblation drop
prototype_plain0/40.90650.2771.500.9830.629
prototype_inhibition0/40.90440.5732.250.7640.733
prototype_inhibition_no_ffn_residual0/40.94530.3911.750.5510.923

结论

随机 prototype + inhibition 可以缓解 collapse，但不能自己发现稳定 rule experts。它否定的是“随机地盘 + 简单竞争就够了”的小版本，不否定“Oracle 地盘 + 守地盘机制”的更强版本。

为什么它会改善一点

  • prototype router 把 expert 选择变成“靠近哪个中心”，比自由线性 router 更像地盘竞争。
  • inhibition 和 homeostasis 会抑制单点垄断，所以 load collapse 有所缓解。
  • ablation drop 上升，说明 expert 路径变得更有因果作用。

为什么它不能真正 work

  • prototype 初始位置随机，不一定落在 rule clusters 上。
  • 训练早期偶然 winner 会被 attraction 进一步强化，随机地盘会被硬化。
  • inhibition 不知道哪个 expert 真正解释哪条 rule，只能扩大 score margin。
  • 所以它能减少 collapse，却不能保证语义对齐。

Oracle-initialized Router 报告

关键正结果

问题

如果 warmup 模型的 rule-context 表示空间里已经有 rule clusters，把 KMeans cluster centers 接到 prototype router 后，能不能真正形成 rule-aligned expert routing？

关键方法修正

必须 warm-start：每个 condition 从同一个 warmup checkpoint 继续，只替换 prototype router。这样 Oracle centers、router 输入、experts 和 LM head 都在同一坐标系。早先把 centers 接到随机新模型的 pilot 不能作为结论。

结论

Oracle-space centers 可以实际诱导 rule-aligned routing。`oracle_init` 是目前支线最强正结果。边界是：如果 warmup cluster 本身不干净，下游 router 很难凭空修复；inhibition 增强 ablation，performance feedback 打开 load，但二者都可能扰动 rule purity。

为什么 Oracle init work

  • 它不再让 prototype 随机出生，而是直接放到 warmup 表示空间的 rule clusters 上。
  • 这给 router 一个明确的 semantic prior：相似 rule-context 应该去同一个 expert，不同 rule-context 应该分开。
  • warm-start 保证 centers、router 输入和 expert weights 在同一坐标系，所以这个 prior 是有效的。
  • cluster 干净的 seeds 上，frozen_oracle_router 和 oracle_init 都稳定四分，说明方法确实把 rule geometry 转成了 routing。

为什么它还不是完整解决

  • seed 2 的 warmup KMeans 本身不干净，Oracle 条件也只到 3 experts，说明上游 representation quality 是瓶颈。
  • frozen_oracle_router routing 很好，但不一定最大化 expert 因果性；inhibition 才明显提高 ablation drop。
  • performance feedback 能打开 load，但会改变 cluster assignment，说明功能约束和语义约束会冲突。
  • 完整 Oracle-MoE 论文还包含 attention semantic group、SVD/oracle projection、locality/CSD 目标，这些没有全部系统验证。
源文件：oracle_initialized_router_experiment_report_zh.md

最终判断

现在可以说

Oracle-space centers 可以实际诱导 rule-aligned expert routing；默认 MoE 失败不是 capacity 问题，也不是单纯 residual 绕路；随机 prototype 和简单 inhibition 不够。

现在不能说

不能说完整 Oracle-MoE 论文方法全部验证；不能说 load balance 就是 expertise；不能说 inhibition/performance feedback 已经解决 specialization。

下一步实验问题 如何在保持 Oracle cluster purity 的同时，提高 expert 的因果性和功能分工？最直接是 `Oracle init + inhibition 系数 sweep` 和 `Oracle init + cluster-preserving performance feedback`。
